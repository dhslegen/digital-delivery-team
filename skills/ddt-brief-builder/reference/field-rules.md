# Brief 字段决策准则

> SKILL.md 的字段提取依赖本表精准决策。每条字段含：从输入提取的策略 / 缺失处理 / 反模式。

---

## §1 项目背景（必填）

**目标**：1-3 句话回答"为什么做 + 解决什么痛点 + 为什么现在做"。

**提取策略**：
- 从输入找痛点关键词："困难"、"低效"、"重复劳动"、"不一致"、"难以追溯"、"耗时"
- 找紧迫性："截止"、"上线"、"合规"、"竞争对手"、"季度目标"
- **反向**：如果输入只描述"做什么"而无"为什么"，需要回过头问用户

**缺失处理**：
- 仅有"做什么"无"为什么" → AskUserQuestion: "这个项目要解决的核心痛点是？"
- 完全空 → 强制问，不允许产出

**反模式**：
- ❌ 编一个看似合理的"为了提升效率"——空洞，没有锚点
- ❌ 重复用户输入做摘要——应该提炼"为什么"层而不是复述

---

## §2 目标用户（必填）

**目标**：主要用户 + 次要用户，每个含角色 + 频率 + 关注点。

**提取策略**：
- 找角色名词：管理员 / 运营 / 客户 / 内部员工 / 开发者 / 设计师 / HR
- 找频率词："每天"、"每周"、"偶发"、"高频"、"低频"
- 找关注点："关注效率"、"关注准确"、"关注合规"、"关注体验"

**缺失处理**：
- 仅有抽象"用户" → AskUserQuestion: "主要用户是谁？（如运营经理 / 内部员工 / B 端客户）"
- 比赛项目 → 默认"评委 + 用户演示"两类

**反模式**：
- ❌ 写"全体用户" / "公众"——下游 design-brief 无法生成 persona
- ❌ 主次都是同一类——区分主次要

---

## §3 成功标准（必填，至少 1 条可量化）

**目标**：项目上线后判断成功的可量化指标。

**提取策略**：
- 优先抓数字：百分比、时长、次数、转化率、留存率、错误率
- 从用户输入的"5 分钟内 / 90% / 不超过 3 次"等短语直接提
- 比赛项目：评分标准就是成功标准（如"完成 X 题得 60 分"）

**缺失处理**：
- 完全空 → AskUserQuestion: "项目上线后如何衡量成功？至少给一个能量化的指标"
- 仅定性"用户满意" → 转成"NPS ≥ 8 / 用户调研满意度 ≥ 80%" + 标注 `<待用户确认>`

**反模式**：
- ❌ 编"DAU > 10000"——除非用户输入含数据，否则不要编
- ❌ "用户体验好" / "性能好"——不可量化，必须转化或问

## §4 核心功能（必填，简单项目 3-7 条；多模块项目按模块归类）

**目标**：一句话动名词描述每个核心功能，不展开实现。

**提取策略（简单项目）**：
- 从输入找动作 + 对象组合："管理成员"、"批量导入"、"审计日志查询"
- 排除技术实现："使用 React" 不是功能；"用户能创建/编辑/查看 X" 是功能
- 比赛项目：把题目拆成核心动作（如"识别图片中的文字"是 1 个功能）

**提取策略（多模块项目，5+ 模块时启用）**：

不强制 3-7 条上限，改用**模块化 markdown** 结构。每模块标 P0/P1/P2 优先级。

**优先级识别信号**：
- ※ / ★ / [必做] / [P0] / "v1.0 范围内" / "本期上线" → P0
- "v1.1" / "下个版本" / "后续规划" → P1
- "v2.0" / "扩展" / "暂不做" → P2

**示例**（无人物流车运营平台，6 模块）：

```markdown
## 核心功能

### 模块 1：运行监测（P0）
- 物流园全局实时总览（车辆 / 网点 / 任务 / 告警 关键指标看板）
- 可视化地图（车辆地理位置 / 运行轨迹 / 实时状态）
- 多维筛选（客户 / 网点 / 车辆状态）
- 实时告警推送 + 弹窗

### 模块 2：任务记录（P0）
- 任务全量记录与查询
- 任务详情（状态 / 进度 / 路线 / 运输日志 / 关键事件）
- 告警过程数据 + 处置入口

### 模块 6：日志管理（P1）
- 操作日志（操作人 / 时间 / 模块 / 动作 / 对象 / 结果）
- 登录日志（登录人 / 时间）
```

**缺失处理**：
- 简单项目不足 3 条 → AskUserQuestion: "还有哪些核心功能没列？"
- 多模块项目某模块缺子功能 → 标 `<待功能清单确认>` + 写软 blocker

**反模式**：
- ❌ 写"用户管理"（太抽象） → 拆成"创建用户 / 修改角色 / 删除用户"
- ❌ 列实现细节："使用 OAuth2 登录" → 改成"用户登录"
- ❌ 多模块项目仍硬塞 7 条 → 用模块化结构，每模块独立列表

## §5 关键约束（必填，至少含 1 类）

**目标**：截止日期 / 工期 / 合规 / 安全 / 性能 / 兼容性 / 团队规模 / 外部接口依赖。

**提取策略**：
- 截止日期：找具体日期或"季度末/月底/下周"
- 工期：找"3 人天 / 2 人月" 类描述
- 团队规模：从人员表（输入类型 J）算总人月
- 合规：找"GDPR / 等保 / SOC2 / 审计追溯"
- 安全：找"脱敏 / 加密 / SSO / MFA"
- 外部接口依赖：含"对接 X 接口"、"取决于 X 能力"、"X 的接口协议"
- 比赛项目：截止日期 = 比赛截止；工期 = 比赛时长

**缺失处理**：
- 完全空 → AskUserQuestion: "项目有截止日期吗？合规要求？"
- 部分缺 → 标 `<需用户补充>` + 写软 blocker

### 工期 reasonability check（v0.9.2 新增）

如果**工期 vs 范围明显不匹配**（典型场景：5 大模块 9 天上线 / 10 人天做 50 个功能），
**必触发软 blocker**：

```markdown
- [BLOCK-BRIEF-RSN-001] 工期 reasonability check 失败：N 模块 × M 子功能 vs T 人天。
  baseline/historical-projects.csv 历史均值显示同等复杂度需 H 工时（约 H/8 人天）。
  建议确认：(a) 是否已有底座（Spring 模板 / Next.js scaffold）/(b) 是否要缩范围 v1.0 / (c) 是否团队规模待补
```

**判定算法**（粗略）：
- 工时 = 模块数 × 8 + 子功能数 × 4（B2B 后台基准）
- 工时 = 屏数 × 6 + endpoint 数 × 2（SaaS 基准）
- 实际工期 < 计算工时 / 0.7 → 触发 reasonability blocker

### 外部接口依赖（v0.9.2 新增）

B2B 项目常含"对接 X 系统"信号。skill 应：
1. 列出每个外部依赖
2. 标注当前确认状态：`已确认接口` / `待技术对接` / `仅有意向`
3. 未确认的接口写**软 blocker**让 /design 阶段优先处理

```markdown
### 外部接口依赖（来自会议纪要 / 合同）

- 车企接口：车辆基础信息同步、行驶路线、视频流（**待技术对接**，影响 §运行监测 实时数据 + §任务记录 视频回放）
- 飞书接口：告警移动端推送（**已部署**，仅需配置 webhook）
- 短信网关：告警短信推送（**仅有意向**，需采购）
```

**反模式**：
- ❌ "尽快上线" → 不可执行，转成"目标 X 月 Y 日"或问
- ❌ "符合行业规范" → 太抽象，要明确具体合规
- ❌ 看到"对接 X" 就当已确认 → 必须问当前状态

## §6 技术栈预设（决策门 D1，必填，详见 SKILL.md）

**值域**：`java-modern | java-traditional | node-modern | go-modern | python-fastapi | interactive | custom`

**速查**：见 `tech-stack-quick-pick.md`

**反模式**：
- ❌ 替用户决定（哪怕输入暗示）——必须用 AskUserQuestion 显式确认
- ❌ 填 `none` 或留空——/design Phase 2 会卡

---

## §7 前端类型（决策门 D2，必填）

**值域**：`spa | server-side | none`

**默认推断**：
- 含"页面/界面/前端/UI/dashboard/管理后台"等词 → `spa`
- 含"管理后台 + Java/JTE/Thymeleaf 模板" → `server-side`
- 含"API/服务/库/CLI/SDK" → `none`
- 不确定 → 用 AskUserQuestion 让用户选

**反模式**：
- ❌ 含 Java 就推 `server-side`——很多 Java 项目也是 SPA + REST
- ❌ 含 SaaS 就推 `spa`——也可能是 server-side rendering

---

## §8 AI-native UI 通道（决策门 D3，仅 frontend.type=spa 时必填）

**值域**：`claude-design | figma | v0 | none`

**速查**：见 `ai-design-quick-pick.md`

**默认**：用户没明确说就推 `claude-design`（v0.8 起首选，零外部账号）。

**反模式**：
- ❌ frontend.type ≠ spa 时还填值——直接 N/A
- ❌ 默认 figma——除非用户已有 Figma 设计

## §9 非目标（可选）

**目标**：明确不做的事，避免下游 PRD 误解。

**提取策略**：
- 从输入找"暂不做"、"不包括"、"v2 再说"、"非目标"
- 主动列：从核心功能里抽抽象层（"不做用户分组管理" / "不做实时协作"）

**缺失处理**：
- 留空 OK，但建议至少列 1-2 条防 scope creep

---

## §10 参考资料（可选）

**目标**：URL / 文件 / 竞品名称 / 设计灵感来源。

**提取策略**：
- 用户给的 URL 直接保留
- 比赛项目：保留官网链接 + 评分标准链接 + 历届优秀作品（如有）
- 已有 PRD 反向提炼：保留 PRD 路径作引用

**反模式**：
- ❌ 编一个"参考阿里 X 项目"——除非用户输入含
- ❌ 把整个 PRD 内容塞进来——只保留**指针**

## 通用准则

### "不可证明则不证明"

DDT 核心原则之一。如果一个字段从输入推断不出，**不要编一个看似合理的值**——
- 标 `<待用户确认>`
- 写软 blocker `- [BLOCK-BRIEF-NNN] <字段> 待用户补充`
- 让 /prd 阶段或用户事后补全

### 字段填充率统计

填充率 = (非空非占位字段数) / 总字段数（10）

- ≥ 90%：高质量，下游 /prd 一跑即过
- 70%-89%：可用，下游可能有 1-2 个 blocker
- 50%-69%：勉强可用，建议产出前再问 1-2 关键字段
- < 50%：质量不足，**不应产出**——回去问用户

### 与 v0.8.1 D5 / v0.8.2 D15 教训对齐

product-agent 实际产出的 PRD 含 `As an 运营经理`（中文 + 反引号 + 中文逗号 + EARS）。
本 skill 写 brief 时应**避免**写得太结构化——保持自然语言段落，让 /prd 阶段的 product-agent 用自己习惯的格式重写。
brief 的"核心功能"段不必用 EARS——用动名词列表就好，product-agent 会展开。

## §11 baseline 增量协议（v0.9.2 新增，应对输入类型 J）

**触发**：用户给的文件含人员需求表 / 工时表 / 项目计划（"项目人员需求计划表.xlsx"等）。

**目的**：把**已知项目的真实工时数据**追加到 `baseline/historical-projects.csv`，让 pm-agent /wbs 阶段的工时估算有更准基线。

### 解析规则

人员表通常列：`姓名 | 部门 | 角色 | 进入时间 | 离开时间 | 人月 | 工作内容`

按角色映射 baseline CSV 的 phase 列：

| 人员表角色 | baseline phase | 备注 |
|---|---|---|
| 项目经理 / 架构 | architecture | 含 design 阶段产出 |
| 产品经理 | requirements | prd + wbs 合计 |
| UI 设计 | design | UI 部分（与架构 design 区分） |
| 前端 | frontend | 多人就累加 |
| 后端 | backend | 多人就累加 |
| 测试 | test + review | 通常 7:3 拆分 |
| 运维 / DevOps | docs（兜底） | 暂无独立列 |

### 计算公式

```
总工时 = 总人月 × 22 工作日 × 8 小时
phase 工时 = 该 phase 角色总人月 × 22 × 8
项目类型（type 列）= B2B 后台 / SaaS / API-only / Mobile / 其他
项目复杂度 = 工时档位（≤60 简单 / 60-200 中等 / >200 复杂）
```

### CSV 行追加

写入 `<project-root>/baseline/historical-projects.csv` 一行（如 baseline 不存在则从插件根 `<DDT_PLUGIN_ROOT>/baseline/historical-projects.csv` 复制后追加）：

```csv
project_id,name,type,total_hours,prd_hours,wbs_hours,design_hours,frontend_hours,backend_hours,test_hours,review_hours,docs_hours,defect_count,coverage_pct,team_size,notes
HIST-NNN,<项目名>,<type>,<总工时>,<prd>,<wbs>,<design>,<fe>,<be>,<test>,<review>,<docs>,,,<人数>,"<备注：人月明细 / 时间窗 / 来源 xlsx>"
```

`defect_count` `coverage_pct` 留空（项目还没跑完，无法填）。

### 用户交互

baseline 增量是**侵入性**操作（修改 baseline 校准数据）。skill 必须用 AskUserQuestion 确认：

```typescript
{
  question: "识别到人员需求表（baseline 信息源）。是否追加到 baseline/historical-projects.csv 作为未来项目工时估算的参考基线？",
  header: "baseline 增量",
  options: [
    { label: "追加（推荐）",
      description: "本次项目作为 HIST-NNN 写入 baseline/historical-projects.csv，让 pm-agent /wbs 阶段更准",
      preview: "总工时 N h / 团队 M 人 / 类型 B2B 后台" },
    { label: "仅写 brief，不动 baseline",
      description: "团队规模与时间窗写到 brief §5，baseline 不变" },
    { label: "完成后再决定",
      description: "项目跑完真实工时与计划工时对比后再决定是否入 baseline" },
  ]
}
```

### 与 brief §5 的协同

无论 baseline 增量与否，人员表的关键信息**必须同时**写到 brief §5：

```markdown
### 团队与工期（来自人员需求表）

- **团队规模**：N 人月（项目经理 X + 产品 X + UI X + 前端 X + 后端 X + 测试 X）
- **时间窗口**：YYYY-MM-DD ~ YYYY-MM-DD（约 N 个月）
- **总工时**：H 小时（按 22 工作日 × 8 小时折算）
- **关键节点**：v1.0 上线 YYYY-MM-DD（前端 + UI 离场日）
```
