## 2. 执行顺序与依赖

```
B1 ──────────► A2 ──┬─► A1 ──► A3 ──► D16+D17 ──► D18 ──► release
(fixtures 先建,    (dry-run 让      (flowchart 派生 (progress  (blocker
 让后续测试用)     A1/A3 都能用     于 commands     可视化用     格式)
                  作产物预览)      frontmatter)    A1+D16 数据)
```

**理由**：
- **B1 first**：先建真实 fixture，让 A1/A2/A3 实现时能用真实数据测，避免 D5→D15 类回归
- **A2 优先级前置**：dry-run 是后续 A1/A3 的产物预览基础——先把每个命令的"读什么/写什么/下一步"标准化
- **A1 → A3**：flowchart 派生需要明确每个命令的依赖关系（A2 的产物），A3 进度可视化基于 A1 的依赖图
- **D16+D17 → D18**：先解决 progress.json 同步，再解决 blocker 格式（D18 依赖 progress 可信）

## 3. atomic 任务拆分

### Phase B1 · fixtures 标准化（3-4h）

**B1-T1**：建 `tests/fixtures/real-agent-outputs/` 目录与索引文件
- 子目录：`prd/` `wbs/` `arch/` `design-brief/` `tech-stack/`
- README.md 含来源标注（哪个项目 + 哪次实战）
- 至少 3 套真实 PRD（来自 ddt-team-admin-v0.8 / v0.8.1 / 一份 v0.7 历史）

**B1-T2**：解析器测试改用 fixture
- `compile-design-brief.test.mjs` 加"对每个 fixture 跑解析"测试
- 期望：每个 fixture 抽到 ≥ 3 stories / visual_direction 非空 / endpoints ≥ 5
- D5/D6/D15 的 fixtures 入库

**B1-T3**：fixture 自动采集 hook
- `bin/collect-fixture.mjs`：当 `DDT_COLLECT_FIXTURE=1` 时复制当前项目 docs/* 到主仓库 fixtures/
- 在 SessionStart hook 提示"是否提交本次 PRD 作 fixture"

### Phase A2 · `--dry-run` 全命令支持（3-5h）

**A2-T1**：抽出共用 `bin/print-dry-run.mjs`
- 接收 `--inputs <a,b>` `--outputs <c,d>` `--next <command>` `--phase <name>`
- 输出 4 段：📥 读取 / 📤 写入 / 📊 emit phase / 👉 下一步

**A2-T2**：每个 phase 命令 Phase 1 加 --dry-run 分支
- 影响 12 个 phase 命令：prd / wbs / design / design-brief / design-execute / build-web / build-api / verify / fix / package / report / impl / kickoff / ship
- 在前置校验之前判断（避免依赖文件存在）

**A2-T3**：契约测试 `tests/unit/dry-run-contract.test.mjs`
- 每个 phase 命令 `--dry-run` 都 exit 0
- 输出含 4 段（📥/📤/📊/👉）
- 不修改任何文件 / 不发 emit-phase 事件

### Phase A1 · flowchart.md 命令依赖图（4-6h）

**A1-T1**：`bin/render-flowchart.mjs` 主体实现
- 解析 `commands/*.md` frontmatter + "建议下一步"段
- 输出 mermaid 流程图（节点：命令；边：建议下一步）
- 含三态分支（spa / server-side / none）的视觉差异化
- 决策门节点（菱形）vs emit 事件节点（圆角）

**A1-T2**：项目级与全局级输出
- 项目级：`/preview --flowchart` 输出 docs/flowchart.md
- 全局级：插件根 `docs/architecture/flowchart.md`（手工提交）
- 自动跑 mermaid lint（`npx @mermaid-js/mermaid-cli` 可选）

**A1-T3**：契约测试 `tests/integration/flowchart-render.test.mjs`
- 每条 commands "建议下一步"必须在 flowchart 里有边
- frontend.type 三态分支必须各自显示
- 新增命令时如果忘了更新会被测试抓到

### Phase A3 · progress 可视化（2h）

**A3-T1**：`bin/render-progress.mjs`
- 输出 ASCII 进度条 + 当前 phase 高亮 + 下一步建议
- 兼容 12 phase（含 design-brief / design-execute）
- 使用 `bin/get-frontend-type.mjs` 决定 spa 路径

**A3-T2**：`/resume` 命令调用此工具
- 替代当前简单的"已完成 N / 进行中 X"文本
- 加测试覆盖三态分支显示

### Phase D16+D17 · progress.json 实时同步（2-3h）

**D16-T1**：phase 命令在 emit-phase --action start 同时调 progress --update in_progress
- 影响 12 个 phase 命令的 Phase 1
- 抽出 `bin/phase-state.mjs` 作为统一入口（emit + update 一起）

**D17-T1**：phase 命令在 emit-phase --action end 同时调 progress --update completed
- 影响所有命令尾部
- 移除 v0.8.1 D8 的 fallback（因为 started_at 现在直接被命令更新，不需 infer 兜底）

**测试**：保留 D8 fallback 路径（兼容旧项目），但新跑的命令应不再触发 duration_estimated

### Phase D18 · blocker 格式统一（1-2h）

**D18-T1**：`templates/blockers.template.md` 加 frontmatter 与"软/硬"区分约定
- 硬 blocker：`- **resolved_at**: null` 含详细字段
- 软 blocker：`- [BLOCK-XXX-NNN] <描述>` 含选项 a/b/c

**D18-T2**：`check-blockers.sh` 加 `--soft` 选项分别报告
- 默认仅检查硬 blocker（保持兼容）
- `--soft` 同时报告软 blocker（不阻塞，仅警告）

**D18-T3**：blockers.md 头部加格式说明，让 design-brief-agent 等知道两种格式语义
