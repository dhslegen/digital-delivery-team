# DDT v0.9 路线图

> **状态**：草稿（2026-05-06）
> **基线**：v0.8.1 实战回归 hotfix 完成
> **决策门**：本文档列出候选方向 + 优先级 + 工时估算，等待用户选定 v0.9 的"主线一拳"
> **作者**：基于 v0.8.0 实战（ddt-team-admin-v0.8）与 v0.8.1 hotfix 评审反思

---

## 1. 总体定位：从"功能正确"到"流程可见"

v0.7 → v0.8 解决了**功能完备性**：契约先行 / Brief 编译 / 3 通道分发 / 决策门 / 进度状态机 / 跨会话接力。
**v0.8.1 实战暴露的下一层问题**不是功能缺失，是**用户对流程整体的可见性不足**：

- D1（design 不导向 brief）：命令间隐式契约用户看不到全貌
- D2（边界模糊）：design-brief / design-execute / build-web 三命令职责让用户困惑
- D3（继续跳错）：状态机推荐不直观
- D7（缺前置守门）：用户能跳过依赖直接跑下游

这些都不是"某个命令坏了"——是"命令网络"作为整体不透明。

**v0.9 主题候选**：把流程从隐式约定升级为**可见、可预览、可解释**的依赖网络。

## 2. 候选方向（按优先级）

### 🎯 V0.9-A：流程可见性（**推荐主线**）

#### A1. flowchart.md 作为正式产物（必做）

**问题**：用户拼不出"prd → wbs → design → design-brief → design-execute → build-web/api → ..."的完整流程图，只能通过命令尾部建议链一步步摸索。

**方案**：
- 新增 `bin/render-flowchart.mjs`：从 `commands/*.md` frontmatter + "建议下一步"段落自动生成 mermaid 流程图
- 输出到 `docs/flowchart.md`（项目级）+ 插件根 `docs/architecture/flowchart.md`（全局）
- 含三态分支（spa / server-side / none）的视觉差异化
- 含决策门节点（菱形）与 emit 事件节点（圆角）
- `npm test` 加入"flowchart 与命令实际链路一致"契约测试

**工时**：4–6 小时
**ROI**：高（新用户上手时间 ↓ 50%；评审报告里 D1/D2/D3 的"隐式契约"全部物化）

#### A2. `--dry-run` 全命令支持（必做）

**问题**：用户不能预览"这个命令会读什么 / 写什么 / 建议下一步是什么"，只能跑了再看。

**方案**：
- 在每个 phase 命令的 Phase 1 末尾加 `--dry-run` 分支：
  ```bash
  if printf '%s' "$ARGUMENTS" | grep -q -- '--dry-run'; then
    echo "## /<command> --dry-run 预览"
    echo "  读取: <input files>"
    echo "  写入: <output files>"
    echo "  emit: <phase events>"
    echo "  下一步: <next command>"
    exit 0
  fi
  ```
- 抽出共用 helper `bin/print-dry-run.mjs`，从 commands frontmatter 派生
- 配套测试：每个 phase 命令 `--dry-run` 都 exit 0 且输出 4 段

**工时**：3–5 小时
**ROI**：中高（让"试错成本"降为 0；新 phase 上线时 dry-run 同时是文档）

#### A3. progress 可视化（建议做）

**问题**：用户跑 `/resume` 看到的是文字进度（"3/10 完成"），不直观。

**方案**：
- `bin/render-progress.mjs` 输出 ASCII 进度条 + 当前 phase 高亮 + 下一步建议
- `/resume` 命令直接调用此工具
- 兼容 12 phase（含 design-brief / design-execute）

**工时**：2 小时
**ROI**：中（边际收益，A1+A2 完成后已经覆盖大部分需求）

**A 方向总工时**：A1 + A2 必做 = 7–11 小时；含 A3 = 9–13 小时

### 🎯 V0.9-B：解析器 fixture 标准化

#### B1. fixtures/real-agent-outputs/

**问题**：v0.8.1 D5/D6 暴露解析器对 product-agent 实际产出的 PRD / brief 格式适应不足。测试用的合成 PRD 不能代替真实 agent 输出。

**方案**：
- 新增 `tests/fixtures/real-agent-outputs/` 目录
- 收集 5+ 真实 PRD（多 agent / 多语言 / 多主题）作为 golden fixture
- 解析器测试改为"对每个 fixture 跑解析"：要求 stories ≥ 3 / visual_direction 非空 / endpoints ≥ 5
- 引入 fixture 自动化采集 hook：`/prd` 完成时如检测到 `DDT_COLLECT_FIXTURE=1`，复制 docs/prd.md 到 fixtures/

**工时**：3–4 小时（不含 fixture 收集本身）
**ROI**：中（防止 D5/D6 类回归）

---

### 🎯 V0.9-C：blocker 决策路径增强

#### C1. blockers.md 结构化

**问题**：v0.8.1 D12 让 agent 失败写 blocker，但 blockers.md 是平铺 markdown，用户不清楚有几个 blocker / 哪个最紧急。

**方案**：
- blockers.md 加 frontmatter：`{open: 3, resolved: 5, latest: 2026-05-06}`
- 新增 `bin/blocker-list.mjs`：列出未解决 blocker 含 phase / 时间戳 / 决策选项
- `/resume` 与 `/doctor` 命令调用此工具，让用户看到全貌

**工时**：3 小时
**ROI**：中（D12 带来的 blocker 路径价值放大）

---

### 🎯 V0.9-D：技术栈预设扩展验证

#### D1. java-traditional + go-modern 实战

**问题**：v0.8 的 5 套 tech-stack-presets 仅 `node-modern` 在 ddt-team-admin-v0.8 实战验证。`java-modern` 在 v3 历史走过但未到 v0.8.1。`java-traditional` / `go-modern` / `python-fastapi` 完全没实战。

**方案**：
- 选 1-2 个未验证的 preset 跑端到端流程
- 收集与 v0.8.1 D1-D12 类似的 issue
- 把 issue 修复合入 v0.9.x 系列（不阻塞主线）

**工时**：1 人天 / 预设
**ROI**：低（验证性质，不引入新能力）；但对插件成熟度有长期价值

## 4. 不在 v0.9 范围

明确**不做**的事项（避免 scope creep）：

- ❌ 重构 progress.mjs 为 SQLite（事件表已在 metrics-agent 用 SQLite，progress.json 保持文本可读）
- ❌ 引入 Web UI（CLI-first 是 DDT 的核心定位）
- ❌ 多租户 / 团队协作（DDT 是单人插件，不是团队后端）
- ❌ AI 设计通道增加第 4 个（现有 3 个已经覆盖主流场景）
- ❌ 自动 PR 创建（合并到 main 是用户的最后一道闸口，不应自动化）

## 6. 体系级反思（来自 v0.8.1 hotfix）

### 6.1 度量层 vs 状态机层的对齐契约

W7.5 R1 修了 emit-phase 但漏了 progress.mjs。这次教训已经写入 `skills/decision-gate/SKILL.md` 的 "新增 phase 命令时的强制对齐 checklist"——未来新增 phase 时 6 处对齐成为强制 checklist。

### 6.2 隐式契约的可见性

12 项缺陷里 5 项（D1/D2/D3/D7/D12）属于命令之间的隐式契约——用户必须靠经验拼出流程图。v0.9-A 主线（flowchart + dry-run）正是把隐式契约**显式化**的方案。

### 6.3 解析器边界假设的脆弱性

D5/D6 都是因为解析器对外部数据格式假设过窄。v0.9-B 主线（fixtures 标准化）是防止此类问题的结构性方案——让真实 agent 产出成为测试的第一公民。

### 6.4 应用范式

DDT 的成熟度提升路径正在显现：

```
v0.5: 能跑（单文件命令 + 黑盒 subagent）
v0.6: 跑得稳（决策门 + 进度状态机 + 跨会话接力）
v0.7: 跑得对（契约先行 + 6-phase 范式 + checkpoint commit）
v0.8: 跑得专业（Brief 编译器 + 3 通道分发 + W7.5 安全加固）
v0.9: 跑得透明（流程可见性 + 解析器加固）   ← 当前候选
v1.0: 跑得通用（多语言预设全实战 + 团队协作可选）
```
